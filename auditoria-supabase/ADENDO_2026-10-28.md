## MED-010 — Evidência corrigida (REEXECUTADO 2026-10-28)

**Query incorreta (sessão anterior):** `view_definition NOT ILIKE '%security_invoker%'` — ERRADA. `view_definition` contém o corpo SQL da view, não as opções do `CREATE VIEW`.

**Query correta:**
```sql
SELECT COUNT(*) FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'v'
  AND n.nspname = 'public'
  AND NOT (c.reloptions @> ARRAY['security_invoker=on']);
```

**Resultado (2026-10-28, produção, sem LIMIT):** **192 views** sem `security_invoker=on`.
Versão anterior com `LIMIT 30` retornava só 30 — mascarava 162 views adicionais.
Exemplos: `ai_insights_cache`, `bi_quotes_summary`, `categories_tree_visual`, `mv_active_products`, `mv_product_cards`, `somarcas_catalogo_publico`, `v_catalog_stats`, `v_products_with_org`, e outras 184.

**Impacto:** Views que fazem SELECT em tabelas com RLS rodam como `SECURITY DEFINER` implícito (owner da view), bypassando as policies RLS do chamador. A propriedade `security_invoker=on` faz a view respeitar as policies do usuário que a chama.

**Proposta de correção:** `P06_views_security_invoker.sql` (AGUARDANDO APROVAÇÃO) — `ALTER VIEW nome SET (security_invoker = on)` para as views que acessam tabelas com RLS.

### P06 — security_invoker=true em 8 views ❌ OBSOLETO

A análise do PO (comment #6701439736) identificou que as migrations posteriores ao audit tornaram esta proposta incorreta:

| View | Razão para NÃO aplicar security_invoker=true |
|------|----------------------------------------------|
| `v_products_public`, `v_suppliers_public` | Migration `20260717151138` explicitamente usa `security_invoker=false` para evitar exposição de `cost_price`/`api_credentials` via SECURITY DEFINER owner. Reverter para `true` quebraria a proteção. |
| `v_kit_component_media_public`, `v_product_compositions_public`, `v_product_properties_public`, `v_product_tags_public` | Migration `20260717161443` exige `security_invoker=false` porque o SELECT de `anon` foi revogado de `products` — com `true` as views executariam como `anon` e falhariam para usuários públicos. |
| `v_system_health_dashboard` | Já corrigida pela migration `20260512201500` (revogado para `anon`/`authenticated`). |
| `v_tabela_preco_gravacao_oficial_public` | Incluída no mesmo contexto de dependência de `products` sem SELECT anon. |

**Situação:** Nenhuma migration foi aplicada ao banco. Estado de produção inalterado.
**Ação:** Proposta de P06 genérica (192 views) não é viável sem análise view-a-view das dependências. Exige nova auditoria com contexto das migrations `20260717*`.
